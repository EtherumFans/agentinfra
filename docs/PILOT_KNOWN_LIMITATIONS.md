# Pilot Known Limitations

**版本**: v1.0-pilot
**日期**: 2026-05-12
**用途**: 试点期间必须向医院方明确告知的系统能力边界
**重要**: 试点人员 (销售、实施、技术支持) 须在演示前阅读并确认理解

---

## 核心原则

iCoDer 当前阶段的定位是 **编码审核辅助系统**，帮助编码员提高审核效率和编码质量，
而非替代编码员的自动编码系统。以下限制必须在试点沟通中主动、明确地告知医院方。

---

## 不能宣称的能力

### 1. 不能宣称自动编码替代编码员

| 属性 | 说明 |
|------|------|
| **限制级别** | 🔴 绝对禁止 |
| **原因** | 当前系统定位为审核辅助，Pipeline 输出编码候选列表，最终编码决策必须经过 Human Review 环节确认。系统不具备独立承担编码责任的准确率和法律合规基础。 |
| **正确说法** | "iCoDer 辅助编码员快速审核编码准确性，编码员的专业判断始终是最终依据。" |
| **错误说法** | "iCoDer 可以自动编码 / 替代编码员 / 不需要人工复核。" |

### 2. 不能宣称医保拒付预测已生产可用

| 属性 | 说明 |
|------|------|
| **限制级别** | 🔴 绝对禁止 |
| **原因** | Denial Management Expert 已集成拒付风险评估模型，但 **未经真实医保赔付数据校准**。拒付预测仅内部评估使用，不可对外宣称能预测或防止医保拒付。 |
| **正确说法** | "iCoDer 在编码审核过程中标记潜在医保合规风险，帮助编码员关注高风险编码组合。" |
| **错误说法** | "iCoDer 可以预测医保拒付 / 降低拒付率 X% / 防止扣费。" |

### 3. 不能宣称真实 DRG 收益提升

| 属性 | 说明 |
|------|------|
| **限制级别** | 🔴 绝对禁止 |
| **原因** | DRG Group Match 评估基于 10 个 demo cases，且以化疗 (Z51.102) 为主，非急性住院病例。当前无法统计系统引入后的 DRG 入组变化带来的真实收益 (RW 提升、CMI 提升、结余增加等)。 |
| **正确说法** | "iCoDer 基于 CHS-DRG 1.1 规则引擎提供 DRG 入组分析，供编码员参考。" |
| **错误说法** | "iCoDer 提升 DRG 权重 X% / 增加医保结余 X 元 / 提升 CMI 值。" |

### 4. 不能宣称临床诊断建议

| 属性 | 说明 |
|------|------|
| **限制级别** | 🔴 绝对禁止 |
| **原因** | 系统由 Rule Engine 和 LLM Agent 提供诊断编码建议，但所有输出均基于 **已存在的病历文本** 进行编码映射和遗漏检测，系统不生成新的临床诊断，不具备临床诊断决策能力。Guard_post 主动拦截含"处方"、"建议用药"、"手术方案"、"剂量"等临床建议性输出。 |
| **正确说法** | "iCoDer 基于现有病历文本，检测可能的编码遗漏和编码选择不当。" |
| **错误说法** | "iCoDer 给出诊断建议 / 临床决策支持 / 诊疗方案推荐。" |

### 5. 不能宣称多院泛化已经验证

| 属性 | 说明 |
|------|------|
| **限制级别** | 🟡 严格限制 |
| **原因** | 当前所有开发和测试均在单套 demo 数据 (10 cases, 4 科室) 上进行。未在不同医院的病案编码实践、不同科室分布、不同编码员习惯上进行跨院验证。 |
| **正确说法** | "iCoDer 当前基于 10 个试点病例验证基础功能，需要通过本次试点积累多科室、多编码员的反馈数据。" |
| **错误说法** | "iCoDer 已在多家医院验证 / 跨院准确率 X%。" |

## 当前技术限制

以下技术限制应在被问及时如实说明:

| # | 限制项 | 影响 | 缓解措施 |
|---|--------|------|---------|
| 1 | WebSocket STT 语音实时编码不可用 | 无法通过语音输入进行实时编码 | 试点以文本病历输入为主，STT 暂不纳入验收范围 |
| 2 | A2A Agent 协同不可用 | Expert 之间无动态协作，按固定 Pipeline 顺序执行 | 已覆盖 7/11 Expert，核心编码审核路径完整 |
| 3 | 前端 E2E 测试未覆盖 | 页面功能仅在本地手动测试验证 | 试点验收通过手动 Checklist 逐项确认 |
| 4 | CI/CD 未部署 | 无自动化构建和部署 | 试点环境由实施团队手动部署和维护 |
| 5 | 并发性能未测试 | 多编码员同时使用时性能未知 | 试点阶段用户数 ≤ 5，无需担心并发瓶颈 |
| 6 | Audit 数据存内存 | 后端重启丢失 Runtime audit chain | 已通过 Export JSON 实现持久化，重要 Review 及时导出 |
| 7 | DRG 分组依赖 OpenDRG 开源引擎 | 分组结果可能与医保局官方分组器有差异 | 标注 "参考分组"，建议与医保实际返回结果交叉验证 |
| 8 | 仅支持 ICD-10-CN + ICD-9-CM-3 | 不支持 ICD-10 国际版及其他编码体系 | 确认医院使用的编码版本后再上线 |

## 试点期间禁止的操作

| # | 禁止操作 | 原因 |
|---|---------|------|
| 1 | 将 AI 编码建议直接写入 HIS/EMR | DUC 机制要求 human_confirm，不可绕过 |
| 2 | 向医院方提供 "准确率 XX%" 的具体数字 | 样本量不足 (10 cases)，数字无统计意义 |
| 3 | 在未脱敏的真实病历上运行系统 | 隐私和数据安全风险 |
| 4 | 修改 guard_post 拦截规则以通过演示 | 安全护栏不可降级 |
| 5 | 宣称系统 "已通过国家医保局认证" | 未取得任何官方认证 |

## 试点沟通话术参考

### 当被问及 "准确率多少？"

> "当前系统基于 10 个试点病例进行了基础验证。我们希望通过这次试点，
> 在更多真实病例上收集编码员反馈，建立可信的评估基线。"

### 当被问及 "能替代编码员吗？"

> "不能。iCoDer 的定位是编码员的辅助工具 —— 就像 Word 的拼写检查，
> 它帮助编码员发现可能的遗漏和不一致，但最终编码决策由编码员做出。"

### 当被问及 "和市面上其他 AI 编码产品比有什么优势？"

> "iCoDer 有两个差异化能力：一是证据链绑定，每个编码建议都能追溯到病历原文；
> 二是 5 层安全框架，确保高风险操作必须经过人工确认。
> 具体的编码准确率需要通过试点数据积累后才能对比。"
